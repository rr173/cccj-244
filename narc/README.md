# narc — 仪器归档离线编目与窄窗读取

为定长二进制仪器归档提供离线编目和按样点区间/列的精确窄窗查询。不使用任何
通用压缩库；线格式见 [FORMAT.md](FORMAT.md)。

## 能力边界

- 查询指定半开样点区间和列，逐位置返回精确值或
  `missing` / `damaged` / `missing_prefix` / `uncovered`，并标注所用块标识；
- 编目绑定不可变来源身份（大小 + 整文件 SHA-256），换版本必须重新编目；
- 窄窗读取只用 `pread` 访问目标块负载，台账记录每个物理读区间和实际字节数；
- 重复小查询从稀疏检查点或入口可信值锚定，不从文件头/列首顺扫，不读无关列；
- 截断、摘要不符、非法行的块整体不可读；下游不能跨过坏前缀借值，但块内可信
  绝对值之后的后缀可读；
- 离线发布（`release`）把获准样点重打包成一批可独立解码的 v1 分件，原档、原
  来源名与解码垫用的私有前值都不外发。
- 离线对账（`reconcile`）把同一次观测的主录/备录两份归档按对齐单映射到逻辑
  样点键，输出需要复核的差异单，每条极值都带可回到原档定位的样点坐标。

## 命令行

```bash
python3 -I narc_tool.py catalog  <archive.narc> <catalog.json>
python3 -I narc_tool.py query    <catalog.json> --start 100 --end 110 \
                                 --columns 1,2 [--full-verify] [--format json]
python3 -I narc_tool.py verify   <catalog.json> [archive.narc]
python3 -I narc_tool.py release  <archive.narc> <authorization.json> <delivery/>
python3 -I narc_tool.py reconcile <alignment.json> <differences.jsonl>
python3 -I narc_tool.py gap-init <workspace> <plan.json>
python3 -I narc_tool.py gap-apply <workspace> <batch.json>
```

查询输出末尾给出 `bytes_read`、物理读区间 `spans` 和触达的块标识，可直接用于
读取边界审计。

## 库接口

```python
from narc import build_catalog, query_window, release_archive, reconcile_archives

build_catalog("feed.narc", "feed.json")
result = query_window("feed.json", start_row=1000, end_row=1008, columns=[1, 4])
for cell in result.cells:
    print(cell.row, cell.column_id, cell.status, cell.value, cell.block_id)
print(result.bytes_read, [(s.offset, s.end) for s in result.spans])

# 离线发布：返回 parts.json 的内容，并把分件原子写入新目录。
manifest = release_archive("feed.narc", "authorization.json", "delivery/")

# 离线对账：把差异单原子写入一个新文件，返回简要统计。
summary = reconcile_archives("alignment.json", "differences.jsonl")
```

## 离线发布（release）

`release` 面向“把获准共享的样点交给外部团队”的场景：输入一个不再变化的
v1 原档、一份 JSON 授权单和一个**尚不存在**的交付目录，产出一批接收端用现有
`catalog` / `query` 就能单独打开的 v1 文件，外加 `parts.json`。

### 授权单

```json
{
  "fragment_id": 7,
  "columns": [1, 2],
  "ranges": [[0, 12], [14, 16]],
  "max_bytes": 200
}
```

- `fragment_id`：唯一指定片段，分件只保留这一个片段身份；
- `columns`：v1 列编号，非空；重复列按一列对待；
- `ranges`：半开样点区间 `[start,end)`，非空且必须落在指定片段内；重叠或相邻
  的区间合并为同一个授权区间；
- `max_bytes`：每个分件（含文件头、片段头、块头、负载和结束标记）的字节上限，
  取值范围 `42` 至 `4294967295`。

### 交付物与安全语义

- `parts.json` 按样点顺序列出每件的 `file`、半开区间、实际 `bytes` 和
  `sha256`；各件区间互不重叠，合起来恰好覆盖授权区间；
- 每件都是自描述 v1 文件，片段来源名统一为 `release`，只含授权片段和请求列；
- 获准列的精确值、显式缺测（`missing`）和无覆盖（`uncovered`）原样保留——
  无覆盖位置没有任何块拥有，绝不写成缺测；
- 每个块都是**独立块**，块内第一条值记录是取自获准样点的绝对值锚，因此分件
  不依赖任何其它分件，也不夹带为解码垫用的私有前值。重建所需的原档前置上下文
  只在发布端内存中使用；
- 不夹带未授权行/列记录、原档路径或原来源名；
- 重建值不受 int64 限制：超过有符号 64 位的精确值仍以增量链保留，绝不截断，
  也不虚构一条假样点作锚（无法在授权范围内锚定的整单拒绝）；
- 获准位置出现坏块、或缺可信前置（`missing_prefix`）时**拒绝整单**，不把它们
  写成缺测；未选到的位置有坏块不单独构成拒绝理由；
- 无解、输入无效或写入失败时不留下最终交付目录：所有写入先落在目标旁的隐藏
  临时目录，全部成功后才一次 `rename` 落位，接收端不可能先拿到部分分件。

### 规划目标与复杂度

只要存在合规切法就会发布。规划在合规方案中先最小化**件数**，件数相同时按样点
顺序取**终点序列字典序最大**的方案。样点号之间可能空出数亿行，规划完全基于
事件（授权区间、请求列、获准覆盖记录），不随纯空档行数增长；分件规划为近线性
`O(N log(N+1))`（逐段二进制倍增跳转表 + 全局边界上的单调双指针扫描）。


## 离线对账（reconcile）

同一次观测有主录和备录两份归档。设备重启后片段的起始编号可能重新计数，通道
也可能换列；按原行号做差会对错样点，直接取第一条又会掩盖同一份归档内部的
矛盾。`reconcile` 按一份**对齐单**把两侧归档映射到逻辑样点键
`(channel, sample)`，输出需要值班员复核的**差异单**（JSONL），每条极值都带
可以回到任一原档定位的样点坐标。

### 对齐单

```json
{
  "left":  {"archive": "/data/primary.narc", "segments": [
    {"fragment_id": 7, "column_id": 1, "local": [5000, 5012],
     "channel": "temp", "global_start": 9000}
  ]},
  "right": {"archive": "/data/backup.narc", "segments": [
    {"fragment_id": 2, "column_id": 3, "local": [0, 12],
     "channel": "temp", "global_start": 9000}
  ]}
}
```

- `left` / `right` 各含一个本地不可变 v1 归档的绝对路径 `archive` 和非空
  `segments`；
- 每段用 `fragment_id`、`column_id`、两端为整数的半开区间 `local: [start,end]`、
  非空字符串 `channel` 和整数 `global_start` 指定对应关系：原样点 `row` 对应
  逻辑键 `(channel, global_start + row - start)`；
- 片段必须存在于归档中，`local` 非空并落在片段声明范围内；编号与映射后的半开
  区间端点都必须在 v1 无符号字段范围内（编号 uint16，样点坐标 uint32）；
- 同侧同片段同列的原区间不能相交（同一个原样点不能在一侧被映射两次）；逻辑
  区间可以自由相交——相交表示这些片段或列对同一样点有多份观测；
- 没有块覆盖的列或位置不凭空产生值，不做插值，也不做单位换算。

### 观测与出单语义

- 值按 v1 重建后的**精确整数**比较，不按原始增量或浮点数比较；显式缺测、无
  覆盖、坏块和缺可信前值（`missing_prefix`）的记录都不算观测；
- 对齐区间之外的记录不进入差异单，但仍可能是区间内增量的可信前置（同块更早
  的绝对值、依赖链上的入口值），解码按 v1 规则照常使用它们；可隔离的坏块整体
  没有可信观测，其依赖后缀仍按 v1 的绝对值恢复规则处理；
- 两侧均无可信值，或两侧各只有一种可信值且相等，不出单；同侧重复出现同一个
  值不算矛盾；
- 其余每个逻辑键写一行：`channel`、`sample`、`kind`、`left`、`right`。任一侧
  有两种或以上可信值时记 `ambiguous`（即使另一侧有相同的值集合），否则按情况
  记 `left_only`、`right_only` 或 `different`；
- 每侧无值用 `null`，有值则为 `{"min": …, "max": …}`；每条极值记录含
  `value`、`fragment_id`、`column_id`、`row`，同值出处有多个时取后三个字段组成
  的元组最小者——凭这三个字段即可回到该侧原档定位样点；
- 出单按通道名的 Unicode 码点顺序、再按样点号升序排列；映射段在对齐单里的
  先后不影响结果。

### 资源与交付保证

- 配置（对齐单）和每份归档的块头索引可驻留内存；观测解码按定长切片流式进行，
  每个通道的合并只驻留每映射段一项、每个逻辑键每侧一份聚合，差异单流式写出——
  工作内存不随单块载荷、观测总量或差异条数增长，耗时也不随空坐标跨度增长；
- 输出路径必须不存在；差异单先写入目标旁的隐藏临时目录，全部落盘后以不可
  覆盖的方式提交，输入无效、归档结构无法解释或读写出错时不会留下正式差异单。

## 补采台账（gap）

仪器值班员按计划补采时，一轮交班可能同时收到迟到的归档、替换掉错误副本、
撤回一批误报。`gap-init` / `gap-apply` 在本地维护一份补采台账，每批收档只
交付**一张变化单**：哪些样点现在要补采（`opened`），哪些原定补采的样点可以
关单（`resolved`）。台账不导出原始样点，也不修改收来的档案。

### 计划

```json
{"range": [0, 1000000], "columns": [1, 4]}
```

- `range`：半开样点区间 `[start, end)`，非空且落在 v1 坐标范围内；
- `columns`：v1 列编号，非空、无重复。

空台账中整个计划区间都待补采。

### 批次

```json
{
  "revision": 7,
  "changes": [
    {"source_id": "probe-a", "op": "upsert",
     "archive": "/data/probe-a.narc", "fragment_id": 3},
    {"source_id": "probe-b", "op": "remove"}
  ]
}
```

- `revision`：从 1 开始连续递增的整数；
- `changes`：非空；同一批不能对同一 `source_id` 做两次操作；
- `upsert`：`archive` 是不可变 v1 归档的绝对路径，`fragment_id` 指定归档内
  一个片段；新增来源或**整体替换**该来源，替换不依赖旧文件；
- `remove`：撤回一个已登记来源，不需要而且不会读取旧归档。同一存档可以登记
  到多个来源名下，各来源分别撤回。

所选片段的样点坐标已经对齐到计划，不做重采样。

### 齐采语义

一个位置只有在**至少一个当前来源的指定片段**中，所有必采列均能读出可信值，
才算齐采。不能拿不同来源的列拼成一帧。显式缺测、无覆盖、损坏块和缺前置
（`missing_prefix`）都不算值；一个坏副本也不能抵消另一个齐采副本。解码完全
沿用 v1 语义：可信绝对值恢复后的有效行照常参与齐采，不因依赖链长而误判。

无法编目的归档或不存在的 `fragment_id` 使整批失败；能编目但标记为损坏的块
按上面的齐采规则处理。`remove` 不存在的来源同样使整批失败。

### 变化单

成功时把 JSON 写到标准输出：

```json
{"revision": 7, "opened": [[12, 20]], "resolved": [[30, 44], [50, 51]]}
```

`opened` 是本批前齐采、应用整批后待补采的样点；`resolved` 正好相反。两组
都按起点升序、合并相邻的半开区间，只在计划范围内计算；无对应变化时为空
列表。变化按**整批前后**比较，所以同一批里一个来源撤回、另一个补上不会产生
先开后关的工单。

### 原子性与重试

台账和该批变化单在同一个 SQLite 事务中提交。非法输入、读写失败或进程在提交
前中断，重开台账都看不到半批。提交完成后若调用者没收到变化单，用**内容逐字节
相同**的 JSON 重试当前最新版本会返回原变化单，且不重新访问任何档案；当前版本
号相同但内容不同、跳号或提交更早的版本都拒绝。允许单机单写，不要求多机协调。

### 增量范围

历史原档处理后可能下线：增量只读取本批 `upsert` 指定的输入，替换或撤回都不
依赖旧文件。计划可能横跨数亿行，空档以事件区间表示，绝不逐行展开。台账按
来源保存各自齐采区间，并把计划切成带“齐采来源计数”的极大区间；处理一批时
只改动本批变动来源的**新旧齐采差异范围**，在这段范围内按区间查其它来源，而
不遍历整份历史来源或不相交的历史范围。

## 测试

```bash
python3 -I tests/test_narc.py
python3 -I tests/test_release.py
python3 -I tests/test_reconcile.py
python3 -I tests/test_gap.py
```

`test_narc.py` 包含：

1. **小数据全量参考核对**：独立参考解码器对所有 30 行 × 3 列、全部
   `465` 个非空窗口做穷举差分，逐位置比较值与四类错误状态；
2. **长增量链末端**：4096 条记录的链只在尾部查询，断言单次窄读、读取上界和
   精确末值；
3. **块中途绝对值**：窗口落在绝对值前后，验证后缀无需读块首即可重建、前缀
   增量为 `missing_prefix`；
4. **孤立坏列**：摘要损坏、截断、非法标签分别注入，验证整块损坏、下游隔离与
   健康列不受影响；
5. **投影与读取边界**：断言所有物理读都落在目标列负载内，重复查询字节数稳定；
6. **身份绑定**：同尺寸篡改被完整哈希捕获，尺寸变化被每次查询的廉价检查拒绝。

`test_release.py` 包含：获准位置的值/缺测/无覆盖逐项对齐、分件脱离彼此独立
解码（含块中途切分与依赖块私有前值恢复）、坏块与缺可信前置整单拒绝、int64
超限精确值保留、对 `60` 组随机用例用暴力 DP 核对“最少件数 + 字典序最大终点”
规划、授权单校验、原子交付与泄漏检查，以及数亿行空档下规划不随行数增长。

`test_reconcile.py` 包含：四种差异类型与免出单情形、缺测/无覆盖/坏块/缺前置
均非观测、区间外可信前置（同块绝对值与跨块依赖链）照常解析增量、坏块隔离与
依赖后缀按 v1 恢复、同侧多值 `ambiguous` 与同值重复免报、极值出处元组最小者
tie-break、通道码点序与样点升序、映射段顺序不变性、对齐单结构/坐标范围/同侧
相交校验、输出路径已存在与不可编目归档时不留正式差异单、小切片解码超大块与
int64 超限精确比较，以及 `60` 组随机含依赖链和损坏块的双档与参考对账器差分。

`test_gap.py` 包含：空台账全区间待补采、显式缺测/损坏块/缺前置的齐采判定、
坏副本不抵消齐采副本、跨来源列不拼帧、同批撤回+补上不产生工单、旧归档下线后
仍可替换与撤回、逐字节重试不访问档案、版本冲突/跳号/更早版本拒绝、非法输入
与不可编目档案不留半批、中断后重开台账只见整批、数亿行空档的事件化处理，以及
`120` 组随机含依赖链和损坏块的档案与参考解码器的齐采区间差分。

## 设计取舍

- 编目只保存标量摘要、稀疏检查点和前缀缺测索引，不保存解码行流；
- 检查点步长固定 256 条记录，窄窗读取量有明确上界而不是仅靠耗时对比；
- 所有重建使用宿主语言任意精度整数，64 位限制只存在于线格式记录负载；
- 损坏块的判断在编目时完成，查询路径不再对其负载做任何 I/O；
- 发布只复用编目元数据做定位，解码读取被限制在与授权相交的可读块负载内，
  分件全部重编码为独立块，原档结构、来源身份与路径均不进入交付目录。
